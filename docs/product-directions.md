# LLM 能力与组织隔离扩展建议

日期：2026-10-30。状态：区分已实现边界与后续方案；公司、组织单元及显式空间授权、受控本机回调与单条补投已落地，其余扩展仍为建议。

## 已实现的边界

第十一阶段已增加空间运行概览和OWNER安全审计查询：全量保留任务、最新交付轮次、数据库待发布消息、失效租约及清理状态，审计按安全列筛选分页。它不包含公司级organization_audit查询、审计detail_json、Broker实时队列深度、趋势或告警；不能将这一只读页面当作完整生产监控。

第十阶段增加到期在线载荷清理：终态输入/结果/回调密文按TTL分批置空，保留业务元数据与审计，活跃责任先按SENT/UNKNOWN结算。代码与隔离验证已完成，源码默认关闭；本机经用户于2026-10-31明确授权开启，并已清除7条过期Fake输入及2条结果正文，未到期载荷与业务事实核对一致。备份/日志/底层页安全擦除和三十天元数据清理仍未实现。

默认 FakeModel 仅摘录输入前几个段落并验证引用。第四阶段新增可配置的 OpenAI 兼容文档分析适配器（配置方式见 README）；第七阶段已以用户配置的型号完成一篇短文真实链路验收，未代表完整效果评测。任务执行、幂等、配额、Outbox、消息恢复、取消与明确重跑，以及第八阶段受控本机签名回调已经实现；这些能力可供后续不同 AI 任务复用。回调仅固定本机目录，第九阶段增加两分钟预览与确认的单条DEAD交付补投；外网目录、批量补投与轮换仍为后续工作。

当前使用共享MySQL/共享表，Tenant作为公司边界，每个Workspace属于一家公司，鉴权同时检查公司成员和直接/组织空间授权。应用、任务、结果、预算、幂等和消息关联保持空间约束；正文加密认证上下文包含空间与任务。它不是独立数据库、独立密钥或独立Broker的物理隔离，公司注册、邀请与计费闭环尚未实现。

OWNER/OPERATOR可以操作任务和读取正文；VIEWER只读安全元数据。用户确认按空间共享，小组需显式授权。公司管理员可管理部门/小组及现有公司成员的组织关系，空间OWNER可配合ADMIN显式授权组织；没有仅本人可见范围。父部门不自动继承权限，多来源取最高角色。

## 适合扩展的 LLM 功能

| 能力 | 使用场景 | 需要验证的结果 |
| --- | --- | --- |
| 深化文档理解 | 提取约束、待办、风险、矛盾和待确认问题 | 结构化输出，每项结论能追溯原文；不能保证发现全部问题 |
| 工单分类与建议 | 分类、优先级建议、推荐处理团队 | 保留人工修正；推荐团队不自动授予数据权限 |
| 文档生成 | 根据技术说明生成测试用例、接口说明、变更摘要 | 草稿可审阅，区分原文事实与生成建议 |
| 团队知识问答 | 检索本空间允许访问的文档后回答问题 | 检索前过滤权限、引用可访问、撤权后失效；权限通过服务端实施 |
| 运维辅助 | 根据安全错误码和已脱敏事件解释失败、建议排查 | 状态来自数据库事实，费用/重试边界由程序决定，不自动执行重跑或危险操作 |

建议先深化现有文档提取并接入真实模型，再增加一个工单分类或生成草稿的任务类型。知识库问答涉及摄取、版本、检索与权限同步，安排在组织隔离之后。是否按此顺序实施仍待下一批需求确定。

未来可增加任务类型及其提示、输出 Schema 和验证器，复用当前执行管道；不提前生成全部插件框架。LLM 不决定鉴权、配额扣减、任务终态或发布副作用。

## 公司、部门、小组和工作空间

已落地区分三个概念：Tenant代表公司边界；Department与Team通过带kind的组织单元保存组织和成员关系；Workspace代表任务、文档和应用的协作范围。部门可选父部门，人员可加入多个部门/小组，父关系不传播数据权限。

示例：公司 A 下有研发部、运营部；研发部包含后端组、前端组。后端组使用后端工作空间，研发与运营可被显式授权到同一个发布协作空间。公司 B 的成员始终不能因为名称相同或猜到 ID 访问公司 A。

Workspace已属于一个Tenant；组织单元通过明确授权获得空间角色。部门标签本身不产生访问权。旧空间各自迁入独立公司，保留ID、原角色和内容；同公司可新建多个空间。workspace_id继续承担内容、预算和消息范围，不混用为公司/部门/小组三类实体。

建议默认空间成员可见；如业务需要，再增加“仅本人、指定小组、指定部门”等显式范围。角色决定可执行的操作，可见范围决定可操作哪些资源，两者分别校验。企业管理员的组织治理权限和正文读取权限也应分开定义。

隔离必须覆盖列表、详情、正文、搜索、导出、预算、配置、后台消息和未来向量检索，不只限制前端菜单。共享数据库方案需在关联关系和查询中保留 Tenant/Workspace 约束；共享队列不会天然提供租户性能隔离，还需按租户配额、公平调度及监控。

后台执行要保留已经受理任务的责任，同时明确撤权对未执行任务、正文读取、知识检索和结果交付的影响。这是待决定的业务策略，不能简单假设所有撤权都取消任务，或所有异步读取都继承无限权限。

## 后续设计需要确定

1. 在已有同公司多空间及显式组织授权之上，是否增加更细的任务可见范围。
2. 是否提供部门负责人治理角色，以及是否限制管理员显式成员变更的提权能力。
3. 新用户邀请、公司注册、组织删除/重组与公司级组织审计查询；空间安全审计查询已实现。
4. 额度按公司统一分配，还是允许部门/小组有硬上限；知识库和模型配置的共享范围。

组织基础链路的迁移、接口、管理页面和负例已实现，证据见verification.md。后续仍先更新spec/tasks/checklist，新增知识检索或任务类型时继续验证跨公司、跨部门/组、撤权与派生结果范围。
