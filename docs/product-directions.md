# LLM 能力与组织隔离扩展建议

日期：2026-10-30。状态：区分已实现边界与后续方案；公司、组织单元及显式空间授权、受控本机回调与单条补投已落地，其余扩展仍为建议。

## 已实现的边界

第十三阶段已支持单条成功任务的分析报告Markdown下载：重新授权读取结论/证据摘录、保留任务配置与时间、拒绝缓存绕过和迟到下载。此能力不增加模型调用、批量导出、输入全文、PDF/Word或下载副本撤回；本地副本不受在线TTL控制。

第十二阶段已支持当前空间完整任务历史：服务端标题/ID字面搜索、状态过滤和时间/ID分页，保留既有最近50条队列。历史只读元数据，点击详情重查权限，不增加正文检索、跨空间查询或全量导出。

第十一阶段已增加空间运行概览和OWNER安全审计查询：全量保留任务、最新交付轮次、数据库待发布消息、失效租约及清理状态，审计按安全列筛选分页。第十四阶段另增当前ADMIN公司组织安全审计查询；它不包含审计detail_json、Broker实时队列深度、趋势或告警；不能将这一只读页面当作完整生产监控。

第十阶段增加到期在线载荷清理：终态输入/结果/回调密文按TTL分批置空，保留业务元数据与审计，活跃责任先按SENT/UNKNOWN结算。代码与隔离验证已完成，源码默认关闭；本机经用户于2026-10-31明确授权开启，并已清除7条过期Fake输入及2条结果正文，未到期载荷与业务事实核对一致。备份/日志/底层页安全擦除和三十天元数据清理仍未实现。

默认 FakeModel 仅摘录输入前几个段落并验证引用。第四阶段新增可配置的 OpenAI 兼容文档分析适配器（配置方式见 README）；第七阶段已以用户配置的型号完成一篇短文真实链路验收，未代表完整效果评测。任务执行、幂等、配额、Outbox、消息恢复、取消与明确重跑，以及第八阶段受控本机签名回调已经实现；这些能力可供后续不同 AI 任务复用。回调仅固定本机目录，第九阶段增加两分钟预览与确认的单条DEAD交付补投；外网目录、批量补投与轮换仍为后续工作。

当前使用共享MySQL/共享表，Tenant作为公司边界，每个Workspace属于一家公司，鉴权同时检查公司成员和直接/组织空间授权。应用、任务、结果、预算、幂等和消息关联保持空间约束；正文加密认证上下文包含空间与任务。它不是独立数据库、独立密钥或独立Broker的物理隔离，公司注册、邀请与计费闭环尚未实现。

OWNER/OPERATOR可以操作任务和读取正文；VIEWER只读安全元数据。用户确认按空间共享，小组需显式授权。公司管理员可管理部门/小组及现有公司成员的组织关系，空间OWNER可配合ADMIN显式授权组织；没有仅本人可见范围。父部门不自动继承权限，多来源取最高角色。

## 适合扩展的 LLM 功能

| 能力 | 使用场景 | 需要验证的结果 |
| --- | --- | --- |
| 深化文档理解 | 提取约束、待办、风险、矛盾和待确认问题 | 结构化输出，每项结论能追溯原文；不能保证发现全部问题 |
| 工单分类与建议 | 分类、优先级建议、推荐处理团队 | 保留人工修正；推荐团队不自动授予数据权限 |
| 文档生成 | 根据技术说明生成测试用例、接口说明、变更摘要 | 草稿可审阅，区分原文事实与生成建议 |
| 团队知识问答 | 检索本空间允许访问的文档后回答问题 | 检索前过滤权限、引用可访问、撤权后失效；权限通过服务端实施 |
| 运维辅助 | 根据安全错误码和已脱敏事件解释失败、建议排查 | 状态来自数据库事实，费用/重试边界由程序决定，不自动执行重跑或危险操作 |

建议先深化现有文档提取并接入真实模型，再增加一个工单分类或生成草稿的任务类型。知识库问答涉及摄取、版本、检索与权限同步，安排在组织隔离之后。是否按此顺序实施仍待下一批需求确定。

未来可增加任务类型及其提示、输出 Schema 和验证器，复用当前执行管道；不提前生成全部插件框架。LLM 不决定鉴权、配额扣减、任务终态或发布副作用。

## 公司、部门、小组和工作空间

已落地区分三个概念：Tenant代表公司边界；Department与Team通过带kind的组织单元保存组织和成员关系；Workspace代表任务、文档和应用的协作范围。部门可选父部门，人员可加入多个部门/小组，父关系不传播数据权限。

示例：公司 A 下有研发部、运营部；研发部包含后端组、前端组。后端组使用后端工作空间，研发与运营可被显式授权到同一个发布协作空间。公司 B 的成员始终不能因为名称相同或猜到 ID 访问公司 A。

Workspace已属于一个Tenant；组织单元通过明确授权获得空间角色。部门标签本身不产生访问权。旧空间各自迁入独立公司，保留ID、原角色和内容；同公司可新建多个空间。workspace_id继续承担内容、预算和消息范围，不混用为公司/部门/小组三类实体。

建议默认空间成员可见；如业务需要，再增加“仅本人、指定小组、指定部门”等显式范围。角色决定可执行的操作，可见范围决定可操作哪些资源，两者分别校验。企业管理员的组织治理权限和正文读取权限也应分开定义。

隔离必须覆盖列表、详情、正文、搜索、导出、预算、配置、后台消息和未来向量检索，不只限制前端菜单。共享数据库方案需在关联关系和查询中保留 Tenant/Workspace 约束；共享队列不会天然提供租户性能隔离，还需按租户配额、公平调度及监控。

后台执行要保留已经受理任务的责任，同时明确撤权对未执行任务、正文读取、知识检索和结果交付的影响。这是待决定的业务策略，不能简单假设所有撤权都取消任务，或所有异步读取都继承无限权限。

## 后续设计需要确定

1. 在已有同公司多空间及显式组织授权之上，是否增加更细的任务可见范围。
2. 是否提供部门负责人治理角色，以及是否限制管理员显式成员变更的提权能力。
3. 新用户邀请、公司注册、组织删除/重组；公司级安全审计已进入第十四阶段，空间安全审计已实现。
4. 额度按公司统一分配，还是允许部门/小组有硬上限；知识库和模型配置的共享范围。

组织基础链路的迁移、接口、管理页面和负例已实现，证据见verification.md。后续仍先更新spec/tasks/checklist，新增知识检索或任务类型时继续验证跨公司、跨部门/组、撤权与派生结果范围。

参考：[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 建议默认拒绝并逐请求验证权限；[AWS 租户隔离说明](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html) 区分登录身份与实际资源隔离。本文组织结构与实施顺序是针对 RelayOps 的设计建议。

## 2026-11-02探索与优先级
当前1.0、Langfuse元数据观测和3条真实模型验收已完成。以下是针对RelayOps的产品判断，只有需求评审已由用户选定进入开发，其余仍为方案。

| 顺序 | 方向 | 实际收益与依赖 | 边界 |
| --- | --- | --- | --- |
| 1 | 需求评审与验收草稿（已实现，2026-11-03） | 将已有缺失/冲突识别变成澄清问题和Given/When/Then，复用现有文本与引用管道 | 人工确认，不自动执行测试或补齐参数 |
| 2 | 文档版本对比与影响分析（已实现，2026-11-03） | 识别语义变化、影响的约束和验收项 | 先实现版本及双输入引用，避免仅比较模型摘要 |
| 3 | 故障解释与排查建议（建议） | 已有安全错误码/尝试/trace可以构成脱敏上下文 | 状态、金额、是否重试由程序决定，LLM不自动重跑 |
| 4 | 工单分类与团队建议（建议） | 将非结构化请求整理为标签和路由建议 | 需人工纠正，团队推荐不产生访问权 |
| 5 | 空间知识问答（建议） | 在历史文档中查找可复用结论 | 需摄取/版本/权限过滤/撤权同步，当前历史只是元数据查询 |

更好的用途是减少评审整理成本，让证据、问题和验收草稿相互关联；摘要仅作导航。鉴权、预算、幂等、状态机和签名计算继续使用确定性代码。评审生成不等于评审完整，引用匹配不等于推理正确；应逐步建立带人工预期的固定样本比较提示词版本。

需求评审已按OpenSpec交付：用途/结果版本冻结、精确引用、人工确认、回调schema及独立输出上限；137后端、88浏览器和4条成功真实评审通过。真实复核同时暴露4096上限下的一次UNKNOWN和一次OUTPUT_TRUNCATED，因此评审输出上限独立为默认8192并纳入profile指纹；该经验说明“是否完整”仍需固定样本评测，而不是仅凭少量成功样本。现已建立20个合成样本的固定评测集、确定性评分器、重复运行和回归比较器。单次运行20/20，但三次重复只有16/20稳定通过（56/60次，2次UNKNOWN、1次截断、1次语义漏项），说明单次结果不能当稳定性结论；10例人工语义复核9通过。下一步是模型对照、跨供应商比较和人工全量复核，而不是直接扩大功能范围。版本对比已完成双输入、双侧引用、影响分析和固定评测集：三次48任务稳定15/16、重复通过97.92%，注入样本一次误列变化；同供应商qwen3.8-flash单次对照已完成：评审17/20、版本14/16，均低于deepseek，且延迟/Token更高、存在超时和重排误报；暂不替换默认模型。下一步是人工全量复核和按模型固定超时的重复对照。

参考主流工具已有[生成测试与故障解释](https://docs.gitlab.com/user/gitlab_duo_chat/examples/)和[代码评审反馈](https://docs.github.com/en/copilot/responsible-use/agents)用途；这些是可借鉴的工作模式，不是RelayOps已经拥有代码库上下文或自动执行能力。[Langfuse离线评测](https://langfuse.com/docs/evaluation/get-started/offline)提供固定数据集/实验比较方式；本地v3功能兼容性仍需逐项验证。
