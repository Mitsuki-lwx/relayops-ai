先建立一个总印象

RelayOps 的核心不是“AI 很聪明”，而是“AI 调用很不确定，但业务责任必须确定”。模型可能超时、断连、返回废话、编造引用、被供应商拒绝；平台要把这些情况翻译成用户能理解的状态，并且保证不重复扣费、不重复外发、不越权读取。

面试时最重要的诚实

这是单机自托管项目，不是生产级高可用集群；是共享库的逻辑隔离，不是物理多租户；是至少一次投递 + 幂等副作用，不是端到端 exactly-once；真实模型只做了少量合成样本验收，不代表准确率。主动说边界，比硬吹“高并发、生产级”更加分。

Glossary first

先看术语：这些词到底是什么意思

不用一次背完。正文里带虚线下划线的词，鼠标悬停、键盘 Tab 聚焦，或在手机上点一下，会显示一句人话解释；本页只是最常用的 18 个。完整表在附录 C。

幂等（Idempotency）同一个操作做多次，结果和做一次一样。像取号纸：同一张号不会排两次队。
事务（Transaction）一组数据库操作要么全成功、要么全失败；不能只写一半。比如任务和待发消息必须一起落库。
Outbox和业务数据放在同一个账本里的“待发消息清单”，防止业务写完但消息丢了。
MQ / RabbitMQ消息队列，负责把“可以执行了”的通知从一个系统传到另一个系统；它不保存正文。
ACK / confirmACK 是消费者说“我处理完了”；confirm 是队列说“我收到消息了”。两个方向，不能互相替代。
租约（Lease）临时工牌：一段时间内你有权干活；过期就换人，旧人不能交结果。
代次（Generation）派工单的版本号；旧版通知不能拿来执行新任务。
SENT / UNKNOWNSENT 表示“可能已经发给供应商”；UNKNOWN 表示“可能做了，但我拿不到可验证结果”。
CSRF防止别的网站借你的登录状态偷偷发请求；写操作必须带一次性令牌。
AES-GCM / AAD一种带完整性校验的加密；AAD 是附加标签，比如“这条密文属于哪个空间/任务”，换任务就解不开。
HMAC用共享密钥给消息做“防伪签名”，接收方可以验证没被改、不是伪造。
SSRF攻击者诱导服务器去访问内网地址。外网回调必须白名单 + 拒绝私网/环回地址。
白名单（Allowlist）只允许名单里的主机，其他一律拒绝；比“黑名单”更适合外发场景。
乐观锁 / 版本号更新前先比对版本；版本变了就返回 409，让用户刷新，而不是覆盖别人的修改。
游标分页记住上一页最后一条的位置，从这里继续查；比“跳过前 N 条”更稳，不会因新增数据重复。
逻辑隔离大家共用一个数据库，但每条查询都带公司/空间条件；不是每家一个独立数据库。
RPO / RTORPO 是“最多丢多少数据”，RTO 是“多久能恢复”；当前只有单机逻辑恢复观测，不是生产 SLO。
评测集 / 基线一组固定样本 + 评分规则 + 历史结果；用来比较提示词/模型改动，不是准确率证书。

01 · Pitch

1.一分钟 / 两分钟 / 十分钟

30 秒版（电梯陈述）

RelayOps 是一个面向开发团队的技术文档异步处理平台。用户提交文档后，平台先把任务可靠落库并返回 202，再通过事务 Outbox 和 RabbitMQ 交给后台执行；模型输出必须带可精确定位的原文引用，结果加密保存并按七天保留期清理。它重点解决的是异步调用中的重复扣费、消息丢失、越权读取和“结果不明”问题。

两分钟版（面试开场）

“我做了一个叫 RelayOps 的单机自托管平台。业务上，它把技术文档转成结构化结论：摘要、关键点、约束、未知项，每条都要能定位到原文；后来又加了需求评审和版本对比：一个把疑似缺漏、歧义、冲突整理成澄清问题和 Given/When/Then 验收草稿，另一个比较基线与修订，输出新增/删除/修改及其影响。”

技术上，它不是同步调模型。受理请求会在一个数据库事务里写任务、预算、幂等记录、Outbox 和审计，提交后才返回 202。后台发布器把消息发给 RabbitMQ，消费者从数据库重新校验任务和代次，领取后先写 PREPARED，再把尝试标成 SENT、把预算从预留转成已用，然后才在事务外调用模型。只要可能已经发出去，结果不明就进入 UNKNOWN，平台不会自动重试，用户必须明确重跑并确认费用。

另外有公司/空间/部门小组的显式授权、AES-GCM 正文加密、七天 TTL 清理、签名回调和单条补投、运行概览和安全审计；1.1 候选又加了 OWNER 可调每日额度、受控外网 HTTPS 回调与签名密钥轮换、版本对比和固定评测集。验证上，当前源码有 151 个后端测试、98 个浏览器测试，使用真实 MySQL、RabbitMQ 和本机 HTTP 桩；1.0 已正式发布，1.1 还只是候选，没有创建 Release。

十分钟版（白板顺序）

  1. 业务问题：文档处理耗时、模型不稳定、团队需要共享与隔离、结果要能核对。
  2. 总体架构：Vue 工作台 → Spring Boot 模块化单体 → MySQL（事实源）+ RabbitMQ（唤醒信号）→ Worker → 模型 / 本机接收端。
  3. 一条主链路：受理事务 → 202 → Outbox → 发布确认 → 消费领取 → SENT → 模型 → 校验 → 保存 → ACK。
  4. 三个边界：事务提交边界、SENT 边界、ACK 边界。每个边界都可能丢东西，所以要有恢复。
  5. 两个防重：幂等键防用户重复提交；代次 + 租约 + 状态条件防消息和执行器重复。
  6. 一个原则：不确定就 UNKNOWN，不自动重试；需要新调用必须显式重跑。
你可以这样理解

把平台想成一家有登记本的快递站：寄件时先在登记本上写清楚“谁、寄什么、寄到哪”，给你一张回执（202）。包裹可能被重复扫描，但登记本上的业务责任只有一份；如果包裹可能已经上车，就不能因为没看到签收就偷偷再寄一份。

02 · Why

2.为什么不是普通 CRUD

普通 CRUD 假设“请求进来，数据库改一下，马上返回”。AI 任务不一样：它慢、会超时、会花钱、结果可能不可用，而且外部副作用无法撤销。

环节普通做法会发生什么RelayOps 的处理
提交请求里直接调模型，等结果浏览器断开、网关超时，用户不知道任务是否还在跑先落库，返回 202 + jobId；后台异步执行
重复点击再建一条任务重复扣费、重复外发Idempotency-Key + 请求哈希；同键同请求返回原任务
消息投递业务写完再发 MQ业务成功、消息没发出去，任务永远排队业务与 Outbox 同事务；发布器补发
重复消息收到就再调一次模型同一任务调用两次，费用翻倍数据库状态 + 代次 + 唯一 SENT 约束；重复消息只 ACK
调用结果不明超时后自动重试供应商可能已经执行，重试造成第二次收费保留 SENT，恢复为 UNKNOWN；不自动重调
保存失败重新调模型拿结果又花一次钱，且结果可能不同同一响应最多重试三次保存；不重新请求模型
权限只在前端隐藏按钮直接调 API 就能读别人正文每个请求服务端重查公司成员、空间角色、正文权限
结果可信度模型说什么就展示什么编造引用、张冠李戴引用必须是真实段落 ID + 原文精确子串，否则失败

五个“如果不管就会出事”的瞬间

窗口 A

受理事务提交后，进程崩了

任务已经在数据库里，但消息还没发。Outbox 里还有一条 NEW，发布器恢复后会补发。用户仍然能用原 jobId 查到 QUEUED。

窗口 B

Broker 确认了，但数据库回写丢了

发布器会重发同一个 messageId。消费者发现任务已经 RUNNING/完成，只 ACK，不再跨过 SENT。重复是允许的，副作用不能重复。

窗口 C

结果提交了，ACK 没送到

Broker 重投。消费者看到数据库已经是 SUCCEEDED，只 ACK。模型调用次数仍然是 1。

窗口 D

SENT 刚提交，进程死了

平台无法证明请求有没有真的发出去，所以恢复为 UNKNOWN，预算从 SPENT 转 UNCERTAIN。不会自动再调用。

面试官最容易追问的点

“你怎么知道消息有没有发出去？” 答案是：不知道。所以不假装知道。能证明的只有数据库事实；不能证明的，就用 UNKNOWN 保留责任，把选择权交给用户。

03 · Users & permissions

3.用户、公司与权限

人话版：三层边界

公司是“大边界”，空间是“干活的地方”，部门/小组是“组织标签”。标签本身不等于权限；必须显式把某个小组授权到某个空间，组员才有角色。父部门不会自动把权限传给子部门。

Tenant / 公司

最外层隔离

每个空间属于一家公司；跨公司访问统一表现成 404，避免泄露“这个资源存在但你没权限”。

Workspace / 空间

任务与正文边界

任务、预算、幂等、消息、密文 AAD 都以 workspace_id 约束；空间也是额度计算单位。

Unit / 部门小组

组织关系

部门/小组只表示组织关系；通过 workspace_unit_grant 显式授予 OPERATOR 或 VIEWER，才产生访问权。

角色能做什么

角色看任务元数据提交/取消/重跑读正文/导出管理目的地/看审计
OWNER可以可以可以可以（本空间）
OPERATOR可以可以可以不可以管理目的地/看审计；可选择交付目标
VIEWER可以不可以不可以（无入口，API 也拒绝）不可以
公司 ADMIN不自动获得不自动获得不自动获得可管理组织；给空间授权还需目标空间 OWNER

三个容易被误解的规则

  • 多来源取最高角色：直接成员是 VIEWER、小组授权是 OPERATOR，则生效 OPERATOR；直接 OWNER 不会被小组 VIEWER 降级。
  • 撤权立即影响后续请求：列表、详情、正文、预算、命令、旧幂等键重放都会重新查当前角色。已经受理的后台任务不会因为用户被撤权就丢掉责任。
  • 公司管理员不是数据管理员：ADMIN 可以改组织关系，但不能因此读空间正文；授权还必须同时是目标空间 OWNER。这不是“不可提权”的治理分权，管理员仍可通过显式成员变更影响权限，所以操作有审计。
边界

当前是共享 MySQL 的逻辑隔离，不是独立数据库/独立密钥/独立 Broker 的物理隔离；也没有公司自助注册、邀请新用户、SSO、公司计费。面试时不要把它说成“完整的多租户 SaaS”。

06 · Lifecycle

6.一个任务的一生

这一段是面试的主线。能按顺序讲清楚 12 步，并指出每一步“崩了会怎样”，就已经超过大多数只讲 CRUD 的候选人。

12 步主链路

  1. 登录 + 取 CSRF

    前端先 GET /auth/csrf，再 POST /auth/login。会话 Cookie 是 HttpOnly、SameSite=Lax；写请求必须带 CSRF token。

  2. 提交任务

    POST /api/v1/workspaces/{workspaceId}/jobs，带 Idempotency-Key。正文、标题、语言、最多三个目的地、是否确认外发、任务用途都在请求里；版本对比还要多带一份 inputTextB。

    输入：无数据库写入

  3. 受理事务：先鉴权，再规范化

    Access.require 重查当前公司成员、直接成员和组织授权；正文做 NFC、换行归一、长度/控制字符校验；版本对比分别校验两份文本，再用 <<<VERSION_A>>>/<<<VERSION_B>>> 组合；幂等键格式校验；对规范化请求做 SHA-256 指纹。

    事务开始

  4. 幂等重放检查

    同 workspace + actor + operation + key 的旧记录：同指纹返回原受理快照；不同指纹返回 409。重放也会重新鉴权，不能用旧成功记录绕过撤权。

    读 idempotency_record

  5. 锁应用与当日预算

    锁住启用中的 application 行；按 Asia/Shanghai 日期建/锁 budget_account；当天额度来自 workspace.daily_limit 策略，OWNER 可在部署硬上限内调整；检查 Outbox 积压上限；尝试 reserved+spent+uncertain < daily_limit，成功才 +1 预留。

    budget_account.reserved +1

  6. 同事务写任务、分录、目的地、Outbox、审计、幂等快照

    插入 ai_job（QUEUED）、budget_entry（RESERVED）、job_destination、outbox_event（generation=1）、audit_event（JOB_ACCEPTED）、idempotency_record（含成功响应 JSON）。任何一步失败全部回滚。

    6 类事实一次提交

  7. 事务提交后返回 202

    Controller 通过 Spring 事务代理返回时，事务已经提交。响应包含 jobId、QUEUED、version=0、payloadExpiresAt。202 的含义是“责任已落库”，不是“模型已完成”。

    事务提交

  8. 发布器 claim Outbox

    每秒扫描 NEW 且到期的记录，FOR UPDATE SKIP LOCKED 领取，写 30 秒发布租约和 claim token。消息只含 8 个字段：schemaVersion、messageId、kind、workspaceId、aggregateId、dispatchGeneration、createdAt、traceId，不含正文。

    outbox_event: NEW → CLAIMED

  9. 发布确认 + mandatory return

    持久化消息发到 direct exchange。只有 publisher confirm ACK 且没有 mandatory return，才把 Outbox 标 SENT；否则保留重发责任，指数退避最多 30 秒并加抖动。

    outbox_event: CLAIMED → SENT

  10. 消费者校验并领取任务

    消费者先按 messageId/workspace/aggregateId/generation/traceId 校验 Outbox 关联；再锁 ai_job，只允许当前 QUEUED、队列未过期、载荷未过期、generation 匹配的消息领取。写 RUNNING、随机 lease_token、lease_until=120 秒，插入 ai_attempt（PREPARED）。

    ai_job: QUEUED → RUNNING；attempt: PREPARED

  11. SENT 事务：先记“可能已发送”

    解密输入、做本地预检、构造模型请求。然后在事务里锁预算、确认仍持有租约、确认载荷仍有效，把 attempt 改为 SENT、预算 reserved→spent、分录 RESERVED→SPENT。提交后才在事务外调用模型。

    attempt: SENT；budget: SPENT

  12. 调用模型 + 心跳

    HTTP 调用不在数据库事务里。心跳每 40 秒续租，最多持续到请求超时 + 30 秒；续租要求 status=RUNNING、token 和 generation 都匹配、租约尚未过期。

    ai_job.lease_until 续期

  13. 校验结果 + 保存

    结构、长度、schema、引用段落 ID、原文精确子串全部通过才保存。结果、SUCCEEDED、审计、Delivery/首 Run/交付 Outbox 在同一事务提交。保存失败只对同一响应重试最多 3 次，绝不重新请求模型。

    ai_result + ai_job SUCCEEDED + delivery

  14. ACK 与读取

    提交成功后手动 ACK。浏览器每 5 秒轮询；任务终态或页面隐藏就停。读正文是独立端点，会重新鉴权、检查 TTL、记录 RESULT_READ 审计。

    无业务写入（读取审计除外）
三种用途在同一管道里怎么分叉

EXTRACT 用一份文本；REQUIREMENTS_REVIEW 也用一份文本，但输出结构是 findings + criteria；VERSION_DIFF 用两份文本，服务端组合成一个加密输入，段落 ID 分别加 a/b 前缀。执行、预算、幂等、TTL、授权、回调完全复用，只是 schema、提示词、profile 和校验器不同。

面试时可以这样收尾

“所以这条链路里，用户看到的 202 只是开始。真正保证正确性的不是 RabbitMQ，而是数据库里的状态、唯一约束和条件更新。MQ 只是让任务更快被看见；即使 MQ 丢了、重复了、ACK 丢了，数据库仍然能恢复或拒绝。”

几个“看起来奇怪但很重要”的设计

  • 消息表不存正文：Outbox 只有 ID、代次、trace。正文在 ai_job 加密列；消息被截获也拿不到文档。
  • 唯一约束比“代码里判断”可靠：同一任务最多一条 SENT 由生成列唯一索引兜底；同一代次只有一条 Outbox 由唯一键兜底。
  • 审计表有 detail_json，但查询 API 不返回：空间审计只取 id/operation/resourceId/actorId/actorName/createdAt 六列；公司审计同理。原因里可能有用户输入，不能顺手带给前端。
  • V1–V8 已部署后不可改：后续 schema 变化只能追加迁移；测试会验证旧迁移 checksum 不变。V8 只加 workspace.daily_limit/budget_version，不改 V1–V7。
  • 复合外键带 tenant/workspace：跨公司父部门、跨公司成员、跨空间任务在数据库层就被拒绝，不只靠应用层。
不要过度解释表数量

面试官问“26 张表是不是过度设计”，不要逐表背。回答：按事实生命周期拆成身份、任务、预算、消息、交付、审计六组；每组有自己的状态和不变量。真正核心的是 8 张表，其余是边界和审计。

08 · Reliability

8.可靠性核心：三个边界、两个防重、一个原则

这是整个项目最值钱的部分。面试时不要只背“用了 RabbitMQ”，要讲清楚每个边界解决的是哪一种“不知道”。

边界 1

数据库事务提交

提交前失败 = 没发生；提交后 = 任务、预算、Outbox、审计一起存在。不能出现“任务有了、消息没有”。

边界 2

SENT

提交 SENT 后，平台承认“请求可能已经发给供应商”。此后失败只能 UNKNOWN，不能自动重调。

边界 3

消费者 ACK

结果提交后 ACK 丢失，Broker 会重投；数据库终态让重投只 ACK，不再次执行。

8.1 幂等：同一张“取号纸”只办一次

人话版

用户点“提交”时，浏览器生成一个随机 Idempotency-Key。如果网络断了，用户刷新后再点，页面会沿用同一个键和同一份请求。服务端发现这个键已经成功过，就把原来的受理结果还给你，不会再建一个任务。

  • 键的范围是 workspace_id + actor_id + operation + idempotency_key；键本身 1–100 位 ASCII。
  • 服务端对规范化后的请求做 SHA-256：字段排序、默认值、NFC、换行归一都会影响指纹；因此“看起来一样”的请求不会误判成同一个。
  • 同键 + 同指纹：返回保存的 response_json（jobId、QUEUED、version、payloadExpiresAt）。
  • 同键 + 不同指纹：409 IDEMPOTENCY_KEY_REUSED，不会偷偷改原任务。
  • 重放也重新鉴权：用户被撤权后，旧键不能绕过 404/403；来源正文过期后，重跑重放也不能绕过 410。
  • 命令（取消、重跑、补投确认）也各有 operation 和指纹；重跑指纹包含资源 ID、版本、原因、风险确认。
面试追问：幂等键能保证“绝对只执行一次”吗？

不能。它保证的是“同一意图不会创建第二个业务根”。真正的执行防重还要靠任务状态、代次、租约和唯一 SENT 约束。幂等键解决用户重复提交；消息去重解决系统重复投递；两者不是一回事。

8.1.1 每日额度：为什么存在，真实业务是否必要

人话版

模型调用要花钱，也可能被脚本刷。平台按“空间 + 自然日”放一个额度阀门：当天最多受理多少次，先预留、再使用、结果不明单独记账。它不是供应商账单，只是平台侧的护栏。

  • 1.0 的额度固定默认 20；1.1 候选改成“空间策略”：OWNER 可在部署硬上限 RELAYOPS_MAX_DAILY_LIMIT（默认 100）内调整。
  • workspace.daily_limit 是策略，workspace.budget_version 是乐观锁版本；budget_account.daily_limit 是当天快照。新的一天按策略建行；当天改策略同步当天行，不改历史日期。
  • 降低额度不得低于当天 reserved + spent + uncertain，否则 422 LIMIT_BELOW_USAGE；版本冲突 409；变更写 BUDGET_POLICY_UPDATED 审计。
  • 额度只控制“平台受理次数”，不控制供应商金额、并发、重试成本；公司总额度、按用户额度、密钥级成本上限仍未实现。
真实业务真的有必要按日吗？

不一定必须“按日”，但必须有某种成本/滥用边界。真实业务更常见的是“按月/按合同额度 + 分钟级限流 + 并发上限 + 全局硬上限/告警”。按日只是当前单机自托管、受控团队下实现简单、语义直观的粗粒度选择；代价是跨午夜取消要释放原受理日额度、日切可能有突发、且不等于供应商账单。

8.2 事务 Outbox：把“业务”和“要发的消息”写进同一个账本

人话版

如果先写任务、再发 MQ，中间崩了，任务就永远没人处理。RelayOps 把任务和“待发消息”放在同一个数据库事务里：要么都成功，要么都失败。后台发布器看到待发消息再慢慢发，发失败就重试。

  • 受理事务同时写：ai_job、budget_entry、job_destination、outbox_event、audit_event、idempotency_record。
  • 发布器每秒跑一次，每批最多 25 条；用 FOR UPDATE SKIP LOCKED 领取，避免多个发布器抢同一条。
  • 领取后写 30 秒 claim_until 和随机 claim_token；发布在事务外做，不把网络 I/O 放进数据库事务。
  • 消息是持久化的，direct exchange 路由到 AI 队列；同时开启 publisher confirm 和 mandatory return。
  • 只有 confirm ACK 且没有 returned 才标 SENT；连接失败、确认超时、不可路由都保留重发责任。
  • 失败退避 1、2、4、8、16、30 秒（封顶 30 秒）再加 0–20% 抖动；同一 messageId 重复发送是允许的。
  • 每空间未发布 Outbox 默认上限 1000；达到上限时新受理返回 503，但原幂等键重放仍可用。
为什么不用“事务消息”或“先发消息再写库”？

事务消息需要 Broker 支持事务或两阶段提交，复杂度高；先发消息再写库会出现“消息到了、任务没提交”的幽灵任务。Outbox 用数据库唯一事实换取了简单、可恢复的至少一次投递，代价是可能重复发送，需要消费者幂等。

8.3 消费者：先从数据库拿执行权，再调模型

  • 消费端手动 ACK，单消费者、prefetch=1，避免同一实例内并发抢任务。
  • 先解码并校验信封：最多 4096 字节、字段必须正好 8 个、schemaVersion=1、UUID 规范、kind 只能是 AI_EXECUTE 或 DELIVERY_SEND。
  • 再校验 Outbox 关联：messageId、workspaceId、aggregateId、generation、traceId 必须与数据库记录完全一致。
  • 然后锁 ai_job：只允许 status=QUEUED、队列未过期、载荷未过期、generation 等于消息代次。领取成功写 RUNNING、lease_token、lease_until，并插入 PREPARED attempt。
  • 如果任务已经 RUNNING/终态，或消息代次落后，消费者直接返回“无需执行”，最后 ACK；不会创建 attempt。
  • 畸形、未知版本、错空间、关联不存在的消息：先在数据库保存 hash + 固定错误码 的安全诊断，再拒绝原消息；隔离队列只收到脱敏通知，不转发原始字节。
  • 数据库异常时不 ACK，关闭 channel，让消息重新入队；容器 5 秒恢复间隔，避免热循环。

8.4 SENT / UNKNOWN：承认“不知道”，比假装知道更安全

人话版

平台在真正调用模型之前，先在数据库写“我准备发了/我已经发了”。如果写完这行就断电，平台无法证明请求到底有没有到供应商。这时唯一诚实的答案是：结果未知。自动重试可能让供应商再扣一次钱，所以平台不做。

阶段数据库事实失败后的状态额度是否自动再调用
领取后、SENT 前RUNNING + PREPARED租约过期 → QUEUED（新代次）或 FAILED（过期/损坏）RESERVED → RELEASED可以重新排队，但仍是同一个任务
SENT 提交后SENT + SPENT租约过期 → UNKNOWNSPENT → UNCERTAIN绝不
结果已保存SUCCEEDED + Result不会回退保持 SPENT不会
关键区别

FAILED = 确定没有可用结果，且平台知道原因（模型拒绝、输出非法、证据不匹配、配置变更等）。UNKNOWN = 请求可能已经到达供应商，但平台拿不到可验证结果。UNKNOWN 不是“失败”，而是“责任未结清”。

8.5 租约与代次：一个管“谁现在有执行权”，一个管“消息是不是当前版本”

机制回答的问题怎么用过期/不匹配的后果
lease_token / lease_until这个执行器现在还有权提交结果吗？领取时随机生成 token，默认 120 秒；心跳每 40 秒续租；提交结果时 WHERE lease_token=? AND status='RUNNING' AND lease_until>NOW()旧执行器迟到写入被拒绝，不能覆盖恢复后的状态
dispatch_generation这条消息还是当前这一代吗？恢复未发送的过期任务时 +1，并写新 Outbox；旧消息代次小于当前代次就忽略旧消息被安全跳过；不会用旧通知重新执行
sent_job_id 唯一索引这个任务是否已经有一条 SENT？生成列只在 sent_at 非空时等于 job_id，并加 UNIQUE数据库层兜底，任何路径都很难制造第二条 SENT
常见误区

“加了代次就能重试 UNKNOWN”是错的。代次只用于还没跨过 SENT 的任务；已经 SENT 的任务即使代次增加，也只能进入 UNKNOWN，不能自动再调用。代次解决“消息新鲜度”，不解决“外部副作用不确定性”。

8.6 取消与明确重跑

取消

只允许 QUEUED

  • 要求 expectedVersion 和 Idempotency-Key
  • 锁“原受理日”的预算行，再锁 Job；与消费者保持同一锁顺序
  • 分录 RESERVED→RELEASED，reserved-1，Job→CANCELLED
  • 已发布/迟到的消息到达后看到终态，只 ACK，不建 attempt
重跑

创建新 Job，不改来源

  • 只允许 FAILED/UNKNOWN，来源正文未过期
  • 要求原因（1–300 字符）和 acknowledgeDuplicateCost=true
  • 新 Job 用当前配置、独立密文、新预算预留、新 Outbox
  • parentJobId 指向来源；来源状态和用量不变

为什么取消要锁“原受理日”的预算？ 任务可能跨午夜排队。取消必须释放任务受理那天的 RESERVED，而不是今天的额度。取消和消费者在数据库里竞争：取消先提交，消费者看到 CANCELLED；领取先提交，取消返回 409。两者只有一个合法结果。

8.7 回调交付：独立责任，不重跑模型

人话版

模型任务成功，不等于结果已经送到接收方。RelayOps 把“保存结果”和“发回调”拆成两条责任：保存结果时，在同一个事务里建 Delivery、首个 Run 和独立的 Delivery Outbox；之后回调失败只推进交付状态，绝不会再调用模型。

  • 两个目录：demo-local-v1 固定本机 http://127.0.0.1:8091/relayops/events；https-allowlist-v1 仅在部署配置 RELAYOPS_DELIVERY_HTTPS_HOSTS 非空时出现。
  • 外网端点必须是 HTTPS、固定路径 /relayops/events、端口 443，不能带用户信息/查询/片段；主机必须在白名单内。创建时校验 URL 形状和白名单，发送前再解析 DNS 并拒绝 IP、localhost、私网/环回/链路本地/组播地址。
  • OWNER 创建/启停目的地、轮换签名密钥；OPERATOR 选择目标；VIEWER 只读元数据。
  • 受理时冻结目标快照（catalog、endpoint、name），最多 3 个不同目标，排序后参与请求指纹；白名单移除或目录变化后旧目的地停止，不静默继续。
  • 结果载荷是 relay.webhook.v1 外壳，不含输入正文；原始 UTF-8 字节只生成一次，SHA-256 与密文持久化。
  • 签名：HMAC-SHA256(secret, "v1\n{timestamp}\n{deliveryId}\n{bodyHash}")，小写 hex；带 X-Relay-Delivery-Id、Run-Id、Attempt-Id、Key-Id、Timestamp、Signature 六个头。
  • 接收窗口五分钟；重试时重新生成时间戳和签名，但正文和 deliveryId 不变；重定向不跟随。
  • 2xx 成功；408/429/5xx/网络未知可重试；其他非 2xx 停止；每个 Run 最多 6 次、总预算 1 小时；退避 1/5/30/120/600 秒 + 抖动。
  • 停用目的地、目录变化、TTL 过期、预算耗尽 → DEAD；租约过期 → Attempt UNKNOWN，旧执行器不能回写。
  • 密钥轮换：OWNER 要求 acknowledgeSecretRead=true 和 expectedVersion；有 PENDING/IN_FLIGHT/RETRY_WAIT 交付时 409 DESTINATION_BUSY；生成新 32 字节密钥、旧密钥立即失效、版本 +1、审计 DESTINATION_KEY_ROTATED，新密钥只返回一次。
不要声称“端到端恰好一次”或“外网回调已完整验证”

平台与接收端没有共享事务。平台保证“至少一次尝试 + 稳定 deliveryId/字节 + 签名”，接收端用 SQLite 按 deliveryId + hash 原子去重，才能让业务保存只发生一次。外网只验证了白名单、SSRF 拒绝、本机签名路径和轮换；真实第三方 HTTPS 证书交付未做端到端验证，DNS 重绑定也未完全防护。

8.8 单条补投：两分钟预览，确认后才新建轮次

  1. 只有最新 Run 是 DEAD、载荷未过期、目的地启用且目录匹配，才允许预览。
  2. 预览要求 expectedVersion 和 1–300 字符原因；服务端生成 2 分钟有效的 replay_plan，绑定操作者、空间、交付版本、目标版本、目录和 payload hash。
  3. 预览不发 HTTP、不建 Run、不建 Outbox。
  4. 确认要求 Idempotency-Key 和 acknowledgeDuplicateDelivery=true；重新检查当前权限、TTL、版本、hash、目录、目标启用状态。
  5. 确认事务里创建 runNo+1 的 PENDING Run、独立 Outbox、根版本 +1、计划 CONFIRMED、审计和幂等快照。
  6. 旧 DEAD Run 和 Attempt 全部保留；沿用原 deliveryId 和原始字节；不创建 Job、不改 AI 额度、不重跑模型。

为什么需要预览？ 补投会造成重复外发，属于不可撤销副作用。两分钟窗口 + 版本/hash 绑定 + 明确确认，是为了让用户在“知道会重复”的前提下做决定，而不是点一下就直接发。

8.9 七天清理：清正文，不清责任

  • 任务受理时写 payload_expires_at = NOW + 7 天；读取、重跑、补投都检查 TTL 和 payload_deleted_at。
  • 清理器默认关闭；启用后每分钟检查，每次最多 25 个终态 Job、25 个已结束 Delivery。
  • 只清 ai_job.input_cipher、ai_result.result_cipher、delivery.payload_cipher，并写删除标记；保留 ID/hash/状态/预算/attempt/审计/交付轮次。
  • 到期但未发送的 QUEUED/未 SENT RUNNING：结算为 FAILED 并释放预留；已 SENT 的：UNKNOWN/UNCERTAIN，不再调用。
  • 迟到结果不能重建已清正文；重复/并发清理最多产生一次审计。
  • SQL 置空不等于磁盘页、redo/binlog、备份、日志、接收端 SQLite 的安全擦除；30 天元数据清理仍未实现。

8.10 哪些“保证”其实没有

听起来像保证实际情况
消息绝不重复不保证。允许重复投递，靠数据库状态和幂等副作用挡住。
模型只调用一次平台保证“每个任务最多一条 SENT”，不保证供应商内部只执行一次；网络不明时就是 UNKNOWN。
回调恰好一次不保证。接收端按 deliveryId+hash 去重，业务效果幂等。
清理后磁盘立即释放不保证。只置空在线列；底层页/备份仍在。
多实例自动高可用没有。当前单实例部署，多实例不在契约内。
AI 结果准确不保证。引用匹配只证明“原文可定位”，不证明语义判断正确。

加密细节

AES/GCM/NoPadding
key   = Base64 解码后的 32 字节（RELAYOPS_MASTER_KEY）
nonce = SecureRandom 12 字节，随密文前 12 字节保存
tag   = 128 bit
AAD   = workspaceId + ":" + jobId + ":input"    // 或 :result / :delivery / :signing-key

把 AAD 绑定到空间、任务和载荷类型，意味着攻击者即使拿到另一条任务的密文，也不能把它挪过来解密。GCM 同时提供机密性和完整性；密文被改一个字节，解密就失败。

当前没有做的

轮询

不是一直刷

11.AI 只生成候选内容，确定性代码负责边界

三种任务用途

EXTRACT

技术文档分析

输出摘要、关键结论、约束、未知项；每条 claim 1–10 条精确引用。默认用途，旧请求指纹保持兼容。

REQUIREMENTS_REVIEW

需求评审与验收草稿

输出最多 6 项 GAP/AMBIGUITY/CONFLICT、澄清问题，以及最多 6 项 Given/When/Then；冲突至少两条不同引用，假设单列并标注待人工确认。

VERSION_DIFF

版本对比与影响分析

基线与修订双输入；最多 8 项 ADDED/REMOVED/MODIFIED，修改必须双侧引用；最多 6 项受影响约束 + 6 项验收草稿。

版本对比的细节

  • 请求用 inputText（基线）和 inputTextB（修订）；只有 VERSION_DIFF 允许第二份文本，其他用途带了会被 422。
  • 两份文本分别按 6000 字符 / 24576 字节限制校验，然后用内部标记 <<<VERSION_A>>>/<<<VERSION_B>>> 组合，存进现有 input_cipher；输入本身含标记直接拒绝。
  • 段落 ID 前缀 a0001/b0001；ADDED 只引用修订侧，REMOVED 只引用基线侧，MODIFIED 必须两侧都有精确引用。
  • 结果版本 version.diff.result.v1；提示词从 version.compat.v1 升到 version.compat.v2，明确把段落重排/空白/格式/注入文本视为非语义变化。
  • 复用评审的 8192 输出上限、一次调用、权限、预算、TTL、回调和脱敏观测；不自动合并、不修改需求、不执行测试。
  • 不新增迁移：用现有 schema_version 冻结用途，重跑按来源 schema 恢复；旧 EXTRACT/REVIEW 结果保持兼容。

模型适配器

  • 只实现非流式 OpenAI 兼容 Chat Completions；system + user 两条消息；user 是包含标题、段落 ID、语言的 JSON。
  • 模型只生成内容；title、modelProfile、schemaVersion 由服务端赋值，防止模型伪造元数据。
  • 普通分析默认 max_tokens=4096；需求评审和版本对比复用独立 RELAYOPS_MODEL_REVIEW_MAX_TOKENS=8192，因为推理型模型可能把内部推理计入输出。
  • 配置 profile 指纹包含地址、模型名、超时、输出上限、token 参数、JSON 模式、提示词版本和提示词；不包含密钥，所以可以轮换密钥而不改变 profile。三种用途各有独立 profile。
  • 受理时冻结 profile；配置变了，旧兼容任务在 SENT 前失败 MODEL_CONFIG_CHANGED 并释放预留；旧 Fake 任务仍可执行。
  • 完整响应体上限 128 KiB；总超时包含响应体；不跟随重定向；应用不自动重试。

引用校验：为什么不是“模型说引用就信”

claim.evidence[i] = { paragraphId: "p0003", quote: "事务提交后才返回 202" }

校验：
1. paragraphId 必须存在于本次输入切分出的段落；
2. quote 必须是该段原文的精确子串（contains）；
3. 每条 claim 至少 1 条、最多 10 条引用；
4. claim 文本非空且 ≤ 2000 字符；
5. 结果 schema/version/字段集合/数组上限全部匹配；
6. 需求评审的 CONFLICT 至少两条不同引用。

14 · Interview Q&A

14.面试问答 76 问：按追问顺序背

先自己回答，再展开对照。答案不是唯一标准，重点是“边界清楚、有证据、不硬吹”。

A. 项目与业务
Q1. 用一句话介绍 RelayOps。

一个把技术文档处理做成可靠异步任务的单机自托管平台：先落库再执行，模型输出必须带精确原文引用，结果可追踪、可授权、可清理、可交付。

Q2. 它解决的核心痛点是什么？

三件事：第一，AI 调用慢且不稳定，不能让 HTTP 请求一直等；第二，重复提交/重复消息/超时重试会造成重复扣费和重复外发；第三，团队共享文档需要真正的服务端权限和可核对的引用，不能只靠前端隐藏。RelayOps 用“数据库事实 + 状态机 + 幂等 + Outbox”把这些边界固定下来。

Q3. 为什么叫 RelayOps？

Relay 是接力：请求从 API 交给 Outbox，再交给 MQ、消费者、模型、交付接收端，每一棒都要有责任记录。Ops 是运维：运行概览、审计、清理、备份恢复、发布门禁。名字强调“接力过程中的可追责”，不是“AI 生成器”。

Q4. 目标用户是谁？

需要把技术文档转成结构化结论的开发/测试/技术写作团队，以及需要做需求澄清和验收草稿的评审人员。角色分 OWNER/OPERATOR/VIEWER：前两者能提交和读正文，VIEWER 只能看安全元数据；公司层还有 ADMIN/MEMBER 治理角色。

Q5. 你在这个项目里负责什么？

从仓库记录看，这是单人独立推进的项目：需求拆分、数据库迁移、后端、前端、测试、发布、运维文档都由同一人完成（文档多次记录 Sol Advisor solo）。面试时建议说“我独立完成了从需求到发布的全链路”，然后立刻补一句“所以我也很清楚它的边界和没做的部分”，避免听起来像团队项目。

Q6. 项目规模多大？

后端主代码约 3300 行 Java、39 个主类；后端测试约 2700 行、18 个测试类；前端约 4600 行 Vue/TS/CSS、19 个源文件；26 张业务表、8 个 Flyway 迁移；1.1 候选当前 151 个后端测试、98 个浏览器测试。规模不算大，但边界完整、失败路径覆盖多。

Q7. 最难的部分是什么？

不是写 CRUD，而是定义“不知道”时怎么办：SENT 后崩溃、消息重复、ACK 丢失、模型超时但供应商可能已执行、撤权与已受理任务冲突。每个问题都要落到数据库状态和可验证的恢复动作，不能靠“应该不会发生”。

Q8. 为什么不做成同步接口？

同步接口把浏览器连接、网关超时、模型延迟绑在一起：用户断开后不知道任务是否还在跑，重试又可能重复调用。异步接口先返回 202 + jobId，任务在数据库里，浏览器退出也不影响后台执行；页面可以轮询状态。

B. 架构与选型
Q9. 为什么是模块化单体，不是微服务？

受理事务要同时写 Job、预算、幂等、Outbox、审计，这些必须在同一个数据库事务里。拆微服务会先引入分布式事务或最终一致，问题更大。当前是单机、受控团队，模块边界清楚即可；等有独立扩缩容/团队边界再拆。

Q10. 为什么用 RabbitMQ，不直接轮询数据库？

首阶段确实用数据库扫描跑通过最小链路；第二阶段换成 Outbox + RabbitMQ，是为了降低领取延迟、把“就绪通知”与业务事务解耦。但数据库仍是事实源：消息只是“可以看一眼”的信号，消费者必须回数据库校验任务、代次和状态。即使 MQ 丢消息，恢复器也能补发。

Q11. 为什么不用 Kafka？

当前是单机、低吞吐、需要按消息做数据库条件领取和手动 ACK；RabbitMQ 的 per-message ack、mandatory return、队列上限更直接。Kafka 更适合高吞吐日志/流处理，不是这个规模的第一选择。换组件要能说清瓶颈，而不是追新。

Q12. 为什么不用 Redis 做分布式锁/队列？

执行权、预算、幂等、Outbox 的正确性都依赖数据库事务和唯一约束；引入 Redis 会多一个一致性边界（Redis 锁过期、主从切换、与 DB 不同步）。当前用 MySQL 行锁 + lease_token + generation 足够，并且能用真实数据库测试证明。

Q13. 事务 Outbox 具体解决什么？

解决“业务提交了但消息没发”和“消息发了但业务没提交”这两个窗口。任务和 Outbox 同事务提交，发布器再从 Outbox 发；发布失败保留责任，租约恢复后重发。代价是可能重复发送，所以消费者必须幂等。

Q14. publisher confirm 和 consumer ACK 有什么区别？

confirm 是 Broker 告诉发布者“我收到了这条消息”；ACK 是消费者告诉 Broker“这条消息我已经处理完，可以删了”。前者解决“消息有没有到 Broker”，后者解决“消息有没有被消费”。两者都丢失时，恢复策略不同，不能互相替代。

Q15. mandatory return 是干什么的？

如果消息到了 exchange 但没有任何队列绑定对应的 routing key，Broker 会把消息退回给发布者。只看 confirm ACK 会误以为“发布成功”，实际上消息不可路由。RelayOps 要求 confirm ACK 且没有 returned 才标 SENT，否则保留重发责任。

Q16. 为什么消息里不携带正文？

正文是敏感数据，消息会在 Broker 磁盘/管理界面/日志里留下副本；一旦 Broker 被访问，正文就泄露。消息只带 8 个关联字段，消费者凭 workspaceId/aggregateId 回数据库解密；这样也避免大消息和消息内容与数据库不一致。

C. 可靠性与分布式
Q17. 你们是 exactly-once 吗？

不是。跨数据库、RabbitMQ、HTTP 供应商，端到端 exactly-once 不现实。我们做的是“至少一次投递 + 幂等副作用 + 数据库状态判定”。消息可能重复，但同一任务最多一条 SENT，重复消息只会 ACK；回调接收端按 deliveryId+hash 去重。

Q18. 同一条消息收到十次，会调用十次模型吗？

不会。第一次领取后任务变 RUNNING；后续消息看到状态不是 QUEUED，直接返回“无需执行”并 ACK。即使消息在任务完成后才到，也不会创建 attempt。测试里有“十次重复信封只调用一次”的用例。

Q19. 发布确认成功但数据库回写丢了，会怎样？

Outbox 仍是 CLAIMED，30 秒租约过期后发布器会重新发同一个 messageId。Broker 可能收到两条，消费者按数据库状态/代次只执行一次。允许重复，但业务副作用不重复。

Q20. 结果保存成功但 ACK 丢了，会怎样？

Broker 重投；消费者看到任务已经 SUCCEEDED/终态，直接 ACK，不调用模型。数据库是最终裁判，不依赖“我记得我 ACK 过”。

Q21. SENT 提交后进程崩了，为什么不能自动重试？

因为无法证明 HTTP 请求有没有真的到供应商。可能没发出去，也可能已经执行并扣费。自动重试会造成第二次调用；所以保留 SENT，恢复为 UNKNOWN，预算从 SPENT 转 UNCERTAIN，让用户明确决定是否重跑。

Q22. FAILED 和 UNKNOWN 的区别？

FAILED 是确定的失败：平台知道没有可用结果，比如模型明确拒绝、输出结构非法、证据不匹配、配置变化。UNKNOWN 是结果不明：请求可能已经执行，但平台拿不到可验证结果。前者可以明确重跑；后者重跑要先承认“可能重复调用/重复收费”。

Q23. 为什么 UNKNOWN 还要占额度？

因为供应商可能已经执行，平台不能假设没花钱。SPENT 转为 UNCERTAIN，表示“平台已使用但结果不确定”；这不是实际供应商账单，只是平台内部额度。真正的费用要以供应商账单为准。

Q24. 租约和代次分别解决什么？

租约回答“这个执行器现在还有权提交结果吗”，用 lease_token + lease_until + 心跳；代次回答“这条消息还是当前这一版吗”，用 dispatch_generation + 唯一 Outbox。租约防旧执行器覆盖新状态；代次防旧消息重新执行。

Q25. 恢复器会做什么？

扫描三类：RUNNING 租约过期、QUEUED 队列过期、QUEUED/RUNNING 载荷过期。未 SENT 的：终止旧 attempt，释放预留，必要时递增代次重新排队；已 SENT 的：UNKNOWN + UNCERTAIN，不重新调用。还会补发“已发布超过 120 秒仍未领取”的 QUEUED 任务。

Q26. 取消和消费者同时发生，怎么保证只有一个结果？

两者都在数据库事务里竞争：取消锁原受理日预算行，再锁 Job；消费者领取也按同样顺序。取消先提交，消费者看到 CANCELLED，不建 attempt；领取先提交，取消看到 RUNNING，返回 409。测试验证只有“取消成功且零 SENT”或“取消 409 且最多一次 SENT”。

Q27. 为什么重跑不直接重置原任务？

UNKNOWN 的不确定性是历史事实，重置会抹掉它；原任务的 SPENT/UNCERTAIN 用量、审计和结果也要保留。重跑创建新 Job，用 parentJobId 关联来源，冻结当前配置，重新预留额度；这样旧账和新账分开。

Q28. 模型超时/断连怎么分类？

明确的 400/401/402/403/404/405/413/415/422/429 → FAILED/MODEL_REJECTED；200 但拒答/截断/非法 JSON/工具调用/伪造引用 → 对应 FAILED；其他状态码、断连、总超时、未知异常 → UNKNOWN/MODEL_RESULT_UNKNOWN。分类只用于安全错误码，不保存供应商响应正文。

Q29. 模型成功但保存失败，会不会重新调模型？

不会。同一个响应在内存里最多重试三次保存；如果仍失败，租约恢复后标 UNKNOWN。绝不为了“再拿一次结果”重新调用供应商。测试里有“迟到结果不能覆盖恢复后的状态”的用例。

Q30. 回调失败会不会重跑模型？

不会。模型结果保存时，Delivery 和独立 Delivery Outbox 同事务创建；之后回调只推进交付状态（PENDING/IN_FLIGHT/RETRY_WAIT/SUCCEEDED/DEAD），不碰 AI 状态、额度和模型调用。

Q31. 回调怎么防伪造和重放？

HMAC-SHA256 签名覆盖 v1、Unix 秒、deliveryId、body hash；接收端校验签名和五分钟时间窗。重放同一 deliveryId + 同 hash 返回已有 2xx，不重复保存；同 ID 不同 hash 返回 409。密钥只通过 OWNER 显式审计接口读取。

Q32. 补投为什么不能直接点一下？

补投会造成重复外发，是不可撤销副作用。需要两分钟预览，绑定交付版本、目标版本、目录、payload hash 和操作者；确认时重新检查权限、TTL、版本和启用状态。这样用户是在“知道会重复”的前提下确认，而不是误触。

Q33. 七天 TTL 到了会怎样？

读取、重跑、补投先检查 TTL 和删除标记，过期返回 410；清理器只对终态任务/已结束交付置空密文并写删除标记。未发送的到期任务结算为 FAILED 并释放预留；已 SENT 的保持 UNKNOWN/UNCERTAIN，不自动重调。元数据、审计、额度、attempt 保留。

Q34. 清理会不会把审计也删了？

不会。清理只置空 input_cipher/result_cipher/delivery.payload_cipher，保留 ID、hash、状态、预算、attempt、交付轮次和审计。删除标记和清理审计同事务。备份/日志/接收端文件不在清理范围。

D. 数据库与并发
Q35. 26 张表是不是过度设计？

按事实生命周期拆：身份/治理、任务/预算、幂等/消息、交付、补投。每张表有不变量和独立生命周期，混在一起会让恢复和审计互相覆盖。真正核心的是 8 张表；其余是边界和审计。规模不大，但拆得有理有据。

Q36. 怎么保证一个任务最多一次 SENT？

除了代码判断，还有数据库兜底：ai_attempt.sent_job_id 是生成列，仅当 sent_at 非空时等于 job_id，并加 UNIQUE。任何路径想插第二条 SENT 都会被数据库拒绝。

Q37. 为什么锁顺序这么重要？

取消/重跑/消费者/交付各有多个行锁；如果顺序相反，会死锁。当前约定：授权/公司 → 应用/预算 → Job → 目的地；交付是 Delivery → Run → Destination → Attempt → Outbox。Outbox 不反向进入业务，事务内不做网络。测试覆盖取消与领取竞争、并发重跑、并发补投。

Q38. 为什么预算行要先锁？

每日额度是并发竞争的共享资源。先锁 (workspace, accepted_date) 的 budget_account，再检查/更新 reserved，能保证并发受理不超过 daily_limit。取消也要锁原受理日的预算行，释放才不会扣错日期。

Q39. 幂等和唯一约束怎么配合？

幂等表防“同一用户意图”创建第二个 Job；唯一约束防“同一代次/同一 SENT”出现重复事实。前者是业务层，后者是数据库层；两层都要有，不能只靠代码 if。

Q40. 分页为什么用 created_at + id？

只看 offset 时，新任务插入会把旧记录往后推，导致下一页重复/漏项。记住本页最后一条的 (created_at, id)，下一页只取排在其之前的记录；时间相同用 id 稳定排序。查询还多取一条（limit+1）判断是否有下一页。

Q41. 审计 ID 为什么用字符串？

数据库 BIGINT 可能超过 JavaScript 的 2^53 安全整数；前端如果转成 Number 会丢精度，导致游标漏项或重复。接口和浏览器都用十进制字符串，服务端再解析成 Long。

Q42. 搜索为什么不用 LIKE '%x%'？

用了 LOCATE(?, column) > 0 + 绑定参数，把 %、_、反斜线当普通字符，避免用户输入变成通配符；中文搜索时把 ASCII UUID 列显式 CONVERT ... USING utf8mb4。代价是没有全文索引，性能不做 SLO 承诺。

E. 安全与权限
Q43. 你怎么防止用户直接调 API 读别人正文？

每个请求在服务端重新算当前角色：用户 enabled + 公司成员 active + 直接空间成员/组织授权，多来源取最高。跨空间/跨公司统一 404；VIEWER 访问 result 直接 403。前端隐藏只是体验，不是权限。

Q44. 为什么跨公司返回 404 而不是 403？

403 会泄露“这个资源存在，只是你没权限”；404 让攻击者无法枚举其他公司的空间/任务。对合法用户来说，看不到就是看不到，体验上也一致。

Q45. 组织 ADMIN 为什么不能读空间正文？

治理权限和数据权限分开：ADMIN 可以管部门/小组/成员，但读正文仍要空间角色；给组织授权还要同时是目标空间 OWNER。否则一个公司管理员可以给自己授权然后读所有文档，治理角色就变成了数据后门。

Q46. 撤权后已经打开的结果怎么办？

下一次请求会重新鉴权；列表、详情、正文、预算、命令、旧幂等键重放都会被拒绝。前端切空间/收到 401/403/404 会清旧结果。已经下载到本地的报告、用户截图/记忆无法撤回，这是产品边界，页面会说明。

Q47. AES-GCM 的 AAD 有什么用？

AAD 绑定 workspaceId、jobId、载荷类型。攻击者把 A 任务的密文挪到 B 任务，解密时 AAD 不匹配就失败；GCM 还提供完整性，改一个字节也会失败。nonce 随机 12 字节，随密文保存。

Q48. 密钥怎么管理？

正文加密的 32 字节主密钥 Base64 放在本地 ops/.env，不提交、不返回前端、不写日志；发布包校验会排除真实 .env。正文主密钥当前不可轮换、无 KMS，丢失旧密文无法恢复。1.1 增加的是回调签名密钥轮换：OWNER 在无活跃交付时生成新 32 字节密钥，旧密钥立即失效。

Q49. 报告导出怎么防 XSS？

所有动态内容放进纯文本代码块，不交给 Markdown 渲染器；围栏长度动态大于内容中最长连续反引号，防止内容关闭围栏；文件名不用用户标题；下载用 Blob + 临时对象 URL，触发后释放。测试覆盖 HTML/script/图片/iframe/javascript 链接和嵌套反引号。

Q50. 日志里会不会有正文/密钥？

不会主动记录。异常只记类型和固定错误码，不打印 SQL 参数/异常 message；模型输出解析失败只记固定原因；API 未知异常返回 traceId，不把堆栈给前端。测试里也有“数据库异常不暴露连接/异常”的负例。

F. 前端与 AI
Q51. 前端轮询会不会把数据库打爆？

只在选中任务且非终态、页面可见时每 5 秒查一次；隐藏就停并清结果，终态停止；运行概览 15 秒刷新、隐藏暂停。当前是受控团队/单机，量级可控；如果规模上来，应该改成 SSE/WebSocket 或推送，而不是无脑缩短轮询。

Q52. 切任务后旧响应回来，怎么防止覆盖新页面？

用 generation 递增 + 请求序号 + 当前上下文（账号/空间/任务/视图/可见性）判断；旧响应不满足就丢弃。读结果还用 AbortController 取消。历史、审计、概览、交付面板都有类似保护。

Q53. 为什么待重试草稿放 sessionStorage？

为了在网络响应丢失/刷新后沿用原 Idempotency-Key 和原请求，避免创建新任务。它按账号隔离，登出/放弃时清除；但它是同标签页明文存储，不是静态加密。更严格的做法是只存键和元数据、不存正文，或者用内存 + 重新输入；这是可改进点。

Q54. AI 准确率多少？

不能给准确率。固定样本上：需求评审单次 20/20，三次 60 个任务 57 成功、稳定 16/20、单次通过 56/60 = 93.33%；版本对比 v2 三次 47/48 成功、稳定 15/16、重复通过 97.92%。同供应商 qwen 对照只有单次。它们证明链路、规则和稳定性基线，不证明业务准确率、所有供应商兼容或生产 SLO。

Q55. 怎么防止模型编造引用？

服务端重新计算：paragraphId 必须存在，quote 必须是该段原文的精确子串；每条 claim 必须有 1–10 条引用；结构/长度/schema 全部校验。伪造会以 EVIDENCE_INVALID 失败，不保存结果、不自动重试。但它只能证明“引用可定位”，不能证明“结论正确”。

Q56. 需求评审和普通分析有什么区别？

用途、提示词、结果 schema、输出上限都独立：评审输出 GAP/AMBIGUITY/CONFLICT、澄清问题、Given/When/Then 和 assumptions；冲突至少两条不同引用；最多 6 项；结果版本 requirements.review.result.v1，提示词 review.compat.v2。重跑保持用途，回调外壳仍是 relay.webhook.v1，用 schemaVersion 区分。

Q57. 为什么评审输出上限是 8192？

真实复核在 4096 下出现一次 UNKNOWN 和一次 OUTPUT_TRUNCATED；推理型模型可能把内部推理计入输出。于是评审独立配置 8192，并纳入 profile 指纹；版本对比复用同一上限，普通分析仍 4096。失败样本没有被算作通过。

Q58. 模型配置变了，排队任务怎么办？

受理时冻结 profile（地址/模型/超时/输出上限/参数/提示词）。执行前发现当前配置与冻结 profile 不匹配，在 SENT 前失败 MODEL_CONFIG_CHANGED 并释放预留；不会静默换模型。旧 Fake 任务仍可执行；明确重跑使用当前配置。

G. 测试、失败与反思
Q59. 测试怎么做的？

规则单测 + 真实 MySQL 集成 + 真实 RabbitMQ 故障 + Playwright 浏览器 + Python 接收端 + 发布/恢复演练。测试库和 vhost 独立，脚本拒绝清理演示库。重点覆盖重复、撤权、超时、旧代次、ACK 丢失、并发竞争，而不是只测正常路径。

Q60. 怎么证明测试不是“自己写自己过”？

用负例和故障注入：同键不同请求 409、跨空间 404、VIEWER 403、十次重复消息只调一次、ACK 丢失不重调、旧 token 不能覆盖、预算并发上限、撤权后旧键重放被拒、报告恶意围栏不逃逸。还用真实 MySQL/RabbitMQ，不是全 mock；测试环境有明确隔离和清理保护。

Q61. 如果流量涨 100 倍，哪里先坏？

先坏的是单实例消费者/数据库连接池和 5 秒轮询。当前 Hikari 最大 6 连接、消费者并发 1、prefetch 1；任务吞吐很低。扩展顺序：先做数据库索引/分区和 Outbox 批量、再把消费者水平扩展（需要保留数据库领取权）、前端改推送、最后才考虑拆服务。不能直接说“加机器”。

Q62. 如果让你重做，会改什么？

三件事：第一，把待重试草稿的正文从 sessionStorage 拿掉，只存键和元数据；第二，补删除式 30 天元数据清理、正文主密钥轮换和物理擦除；第三，补真实第三方 HTTPS 证书交付、公司总额度和并发限流，而不是继续加任务类型。架构上不会先拆微服务。

Q63. 这个项目最能体现你什么能力？

把不确定的外部调用拆成可验证的状态和责任边界；用数据库约束而不是口头承诺保证正确性；能写代码，也能写 ADR、测试、发布/恢复文档；知道什么时候不该引入新技术。这些比“会调 API”更难。

Q64. 怎么向非技术同学解释？

“你把文档交给平台，平台先给你一张回执，说明已经登记；后台慢慢处理。处理成功会给你带原文出处的结论；如果中途不确定有没有处理完，平台不会偷偷再交一次，而是标成‘结果未知’，让你决定要不要重新提交。团队里谁能看、谁能改，也由平台按公司和空间检查，不靠页面按钮藏起来。”

H. 1.1 新增能力
Q65. 版本对比和普通分析、需求评审有什么区别？

普通分析是单文本 → 摘要/关键点/约束/未知项；需求评审是单文本 → 问题/澄清/验收草稿；版本对比是双文本 → 新增/删除/修改 + 受影响约束 + 受影响验收草稿。三者共用同一条执行管道，但 schema、提示词、profile、校验器不同。版本对比的段落前缀是 a/b，ADDED 只引用修订、REMOVED 只引用基线、MODIFIED 必须双侧引用。

Q66. 版本对比为什么把两份文本组合进一个加密列？

为了不新增迁移，也不复制一套任务表。服务端把两份文本用内部标记组合后存进现有 input_cipher，段落 ID 分别加前缀；读取和 Worker 按 schema_version 选择解析方式。代价是内部格式必须严格，输入里出现保留标记就直接拒绝，不能静默转义。

Q67. 版本对比为什么不自动合并或替用户选择？

它是“影响分析草稿”，不是变更决策器。模型可能漏报、误报、把重排当变化；自动合并会掩盖冲突，自动选版本会替用户做业务决策。所以只输出变化、影响和待确认草稿，明确标注人工确认，不修改需求、不执行测试。

Q68. OWNER 可调每日额度，为什么还要部署硬上限？

OWNER 最了解团队当天要跑多少任务，但平台不能让单个空间无限放大成本/滥用风险。部署级 RELAYOPS_MAX_DAILY_LIMIT 是平台护栏，空间策略只能在上限内调整。降低额度不得低于当天已占用，避免把已预留/已用/未知的账做成负数；版本冲突用 409，变更写审计。

Q69. 外网 HTTPS 回调怎么防 SSRF？

只允许部署配置的白名单 DNS 主机，端点必须 HTTPS、固定 /relayops/events、443，不能带用户信息/查询/片段。创建时校验 URL 形状和白名单；发送前再解析 DNS，拒绝 IP、localhost、私网/环回/链路本地/组播地址；不跟随重定向。白名单移除或目录变化后旧目的地停止。限制是 DNS 重绑定仍未完全防护，生产要配受控主机、网络出口策略和接收端验签。

Q70. 回调签名密钥怎么轮换？

OWNER 提交 acknowledgeSecretRead=true 和当前 expectedVersion；服务端检查没有 PENDING/IN_FLIGHT/RETRY_WAIT 的活跃交付，否则 409 DESTINATION_BUSY；生成新 32 字节密钥、替换密文、version+1、写 DESTINATION_KEY_ROTATED 审计，新密钥只返回一次。旧密钥立即失效，没有宽限窗口，所以接收端要同步更新。

Q71. 备份恢复的 RPO/RTO 是多少？

不能给生产 SLO。当前只做了本机逻辑恢复观测：27 表、779,666 字节，备份 976ms、恢复 7,037ms、再导出 455ms、总计 8,680ms；完整有序 SQL 和密文 hash 一致。RPO 实际是“最近一次成功备份”，没有 binlog/PITR；RTO 不含停机决策、跨机传输、DNS/TLS、主密钥恢复和接收端去重库。跨机、磁盘满、网络分区、备份加密都未验证。

Q72. 30 天元数据清理做了吗？

没有做删除，只做了只读盘点。删除会破坏预算、幂等、交付和审计链，必须先明确哪些字段必须保留、哪些可以删，并获得用户授权。脚本 metadata-retention-inventory.mjs 只统计超过天数的终止任务及依赖行，没有删除路径；本轮主库 0 行超过 30 天。

Q73. qwen 和 deepseek 的对照结论是什么？

同供应商、同提示、同固定样本的单次对照：需求评审 deepseek 20/20，qwen 17/20；版本对比 v2 qwen 16/16，deepseek 15/16。但 qwen 评审平均约 87.5 秒、版本约 27.8 秒，Token 更高，且只有单次运行、稳定性未测。结论是当前不替换默认模型，不是“qwen 全面更差”。

Q74. 评测集通过 20/20，能说明什么？

只能说明“在这个固定样本、这个提示词/配置、这次运行里，评分规则通过”。需求评审单次 20/20，但三次后稳定 16/20；版本对比 v2 三次 47/48 成功、稳定 15/16。评分器只覆盖预定义关注点，注入只有一种模式，人工复核样本也少。正确说法是“固定样本上的基线”，不是“准确率 100%”。

Q75. 1.1 已经发布了吗？

没有。1.0.0 是 2026-11-02 正式发布；1.1.0 是 2026-11-04 的源码候选（提交 35541f2），有 151 后端/98 浏览器、17 文件包和 SHA256 记录，但没有创建 tag/Release。面试时要说“候选/源码已实现”，不能说“1.1 已上线”。

Q76. 每日额度真实业务真的有必要按日吗？

不一定必须按日，但必须有某种成本/滥用边界。真实业务更常见的是“按月/按合同额度 + 分钟级限流 + 并发上限 + 全局硬上限/告警”。按日是当前单机自托管、受控团队下实现简单、语义直观的粗粒度选择；代价是跨午夜取消要释放原受理日额度、日切可能有突发，且不等于供应商账单。

15 · STAR

15.五个可以讲 5 分钟的 STAR 故事

故事 1：SENT 边界与 UNKNOWN

Situation最初链路是“领取任务 → 调模型 → 保存结果”。如果进程在调用前/调用后崩溃，无法判断供应商是否已经执行；自动重试可能重复收费。
Task在不引入分布式事务的前提下，让“可能已调用”的状态可解释、可恢复、不重复扣费。
Action把调用拆成三步：短事务领取并写 PREPARED；新事务把 attempt 标 SENT、预算 reserved→spent；事务外调用模型。恢复时看是否存在 SENT：没有就重新排队/释放；有就 UNKNOWN/UNCERTAIN，绝不自动重调。结果保存用 lease_token + status 条件更新，旧执行器迟到写入被拒绝。
Result测试覆盖“SENT 后崩溃”“ACK 丢失”“旧 token 迟到”“重复消息十次”等场景；同一任务最多一条 SENT。代价是 UNKNOWN 需要用户明确重跑，但避免了不可控的重复费用。

故事 2：4096 输出上限导致真实失败

Situation需求评审真实复核时，同一模型在 4096 输出上限下出现一次 MODEL_RESULT_UNKNOWN、一次 OUTPUT_TRUNCATED；功能看起来“时好时坏”。
Task区分“模型能力问题”和“配置上限问题”，不能靠放宽校验或自动重试掩盖。
Action保留失败任务和用量，不复活、不退款；新增独立 RELAYOPS_MODEL_REVIEW_MAX_TOKENS（默认 8192），纳入评审 profile 指纹；失败样本不计为通过，修复后用新任务复验。
Result最终配置下评审样本成功；失败样本成为“为什么要独立输出上限”的直接证据，而不是被隐藏。面试时可强调“失败驱动设计”。

故事 3：撤权与并发受理的锁顺序

Situation组织成员被移出公司时，另一个请求正拿着旧幂等键等待受理；如果先读旧快照再等锁，可能在撤权提交后仍然创建任务。
Task让撤权和受理线性化，且不引入死锁。
Action写命令先用共享锁当前读定位空间的公司归属，再锁公司行和当前直接成员；统一锁顺序“授权/公司 → 应用/预算 → Job”。测试在公司锁内移出成员，并在提交前启动旧键重放，验证请求等待撤权提交后返回 404，没有新增 Job。
Result撤权立即影响后续交互；已受理后台任务仍履行责任。代价是每家公司写命令串行，当前规模可接受。

故事 5：版本对比真实失败与提示词 v2

Situation版本对比首轮真实运行 11/16；提示词 v1 下模型常把段落重排/格式变化当语义变化，也常省略受影响验收草稿。
Task区分“评分规则问题”“提示词问题”“模型能力问题”，不能用放宽校验掩盖。
Action修正 rubric；在 version.compat.v2 明确“重排/空白/格式/注入文本不是语义变化”，要求可测试变化至少给一条验收草稿；保留失败样本和用量，不自动重试；三次独立运行后再比较。
Resultv2 三次 47/48 成功、稳定 15/16、重复通过 97.92%，唯一失败是一次重排样本输出无效；注入样本 3/3 通过。没有把单次 16/16 说成稳定结果。

面试前自测 8 题

1. 为什么返回 202 之前必须提交事务？

否则用户拿到 jobId，数据库里却没有任务；浏览器断开后无法追踪。提交后才返回，保证“回执”对应真实责任。

2. confirm ACK 和 mandatory return 分别防什么？

confirm 防“Broker 没收到”；returned 防“到了 exchange 但没有队列可路由”。两者都通过才标 SENT。

3. 为什么 SENT 后不能自动重试？

请求可能已到供应商并执行；自动重试会重复调用/重复收费。只能 UNKNOWN，用户明确重跑。

4. 租约和代次有什么区别？

租约管“当前执行器有没有权写结果”；代次管“消息是不是当前版本”。一个防旧写入，一个防旧消息。

5. 取消为什么要锁原受理日预算？

任务可能跨午夜排队；释放的是受理当天的 RESERVED，不是今天的额度。

6. 重跑为什么创建新 Job？

保留原 UNKNOWN/FAILED 的不确定性、用量和审计；新 Job 用当前配置和独立额度，parentJobId 关联来源。

7. 回调怎么做到“业务效果幂等”？

平台至少一次 + 稳定 deliveryId/字节 + HMAC；接收端按 deliveryId+hash 原子去重。不是共享事务的 exactly-once。

8. 这个项目最大的局限？

单实例、共享库逻辑隔离、单主密钥、无 30 天元数据清理/物理擦除、真实模型评测样本少。主动说，别等面试官挖。

附录 C：术语表（给非技术读者）

术语人话解释
异步任务你先把事情交出去，拿一个编号；不用站在原地等，之后用编号查进度。
幂等同样的操作做多次，效果和做一次一样。像取号纸：同一张号不会排两次队。
事务一组数据库操作，要么全部成功，要么全部失败；不能只写一半。
Outbox和业务数据放在同一个账本里的“待发消息清单”，防止业务写完但消息丢了。
MQ / RabbitMQ消息队列，负责把“可以执行了”的通知从一个系统传到另一个系统。
ACK消费者告诉队列“这条我已经处理完了，可以删”。
Publisher confirm队列告诉发布者“我收到这条消息了”。
租约 / lease临时工牌：一段时间内你有权干活；过期就换人，旧人不能交结果。
代次 / generation派工单的版本号；旧版通知不能拿来执行新任务。
UNKNOWN“可能已经做了，但我不能证明结果”，不能当成失败直接重来。
TTL保留期；到期后在线正文会被清掉。
AES-GCM一种带完整性校验的加密方式；改一个字节就解不开。
AAD加密时附带的“标签”，比如这条密文属于哪个空间/任务；换任务就解不开。
CSRF防止别的网站借你的登录状态偷偷发请求；写操作要带一次性令牌。
HMAC用共享密钥给消息做“防伪签名”，接收方可以验证没被改、不是伪造。
幂等键一次提交意图的身份证；网络断了重试时沿用同一个。
游标分页记住上一页最后一条的位置，从这里继续查；比“跳过前 N 条”更稳。
逻辑隔离大家共用一个数据库，但查询都带公司/空间条件；不是每家一个独立数据库。
至少一次消息可能送两次，但不会故意漏；重复由业务幂等处理。
恰好一次理想状态：不重不漏。跨网络/数据库很难真正做到，不要随便宣称。
Fake 模型本地确定性假模型，只摘录段落，不调用供应商；用于验证工程链路。
OpenAI 兼容按 Chat Completions 的请求/响应格式对接，不代表所有供应商都完全一样。
证据 / evidence结论对应的段落 ID + 原文片段；用来让人核对，不是让模型自证。
Langfuse可选的观测工具；只发阶段/模型/用量等元数据，不发正文。
SSRF攻击者诱导服务器去访问内网/本机地址；外网回调必须白名单 + 拒绝私网/环回。
白名单 / Allowlist只允许名单里的主机，其他一律拒绝；比黑名单更适合外发场景。
DNS 重绑定域名第一次解析到公网、之后解析到内网，试图绕过 URL 检查；发送前再次解析只能降低风险，不能完全消除。
乐观锁 / 版本号更新前先比对版本；版本变了返回 409，让用户刷新，而不是覆盖别人的修改。
RPO / RTORPO 是“最多丢多少数据”，RTO 是“多久能恢复”；当前只有单机逻辑恢复观测，不是生产 SLO。
评测集 / 基线固定样本 + 评分规则 + 历史结果；用来比较提示词/模型改动，不是准确率证书。
Profile模型配置指纹：地址、模型名、超时、输出上限、提示词版本等；受理时冻结，配置变了旧任务不会静默换模型。
VERSION_DIFF版本对比用途：基线与修订双输入，输出新增/删除/修改、受影响约束和验收草稿。
